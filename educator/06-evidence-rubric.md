# Submission evidence rubric

This rubric is designed for human review. It should not be converted mechanically into a misconduct score.

| Evidence category | Strong evidence | Weak or missing evidence |
|---|---|---|
| Authored scope | Included/excluded files are transparent; `.codeprobeignore` is appropriate | Dependencies, starter code or generated files appear in the analysed set |
| Development history | Commits or logs show gradual implementation, debugging and revision | One-shot final code with no intermediate artefacts |
| Design explanation | Student can explain architecture, data flow and trade-offs | Student can only paraphrase surface behaviour |
| Testing evidence | Meaningful tests, manual checks or reproducible examples are present | No tests or only trivial happy-path runs |
| AI disclosure | Assistance is specific, bounded and linked to human revision | Assistance is undeclared, vague or inconsistent with code style |
| Code walkthrough | Student can explain selected functions, edge cases and failures | Student cannot explain core logic or error handling |
| CodeProbe report | Trigger status is interpreted with included/excluded files and metric roles | Score is treated as a standalone verdict |

A strong submission need not have a very low CodeProbe score. It should have coherent code, defensible authorship evidence and a student who can explain the work.
